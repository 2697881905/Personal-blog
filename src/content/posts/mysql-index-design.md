索引不是字段旁边的一个勾选项，而是为特定查询维护的一套有序数据结构。设计索引前，先列出高频 SQL、过滤条件、排序方式和返回字段。脱离查询讨论“哪个字段适合建索引”，往往只能得到局部正确的答案。

## 先固定查询，再讨论字段

同一张表可能同时服务点查、列表、统计和后台导出。它们的代价模型不同，不能用一条 SQL 代表全部。把查询按形状分组：

- 点查：主键或唯一键定位单行，关注回表次数。
- 列表：等值过滤加排序和分页，关注扫描范围与排序成本。
- 范围统计：时间窗口聚合，关注覆盖范围和临时表。
- 后台导出：大结果集顺序读，关注 I/O 与锁的范围。

每条查询至少记录 SQL 模板、参数分布、执行频率、返回列和可接受延迟。参数分布比平均值更重要：`status` 取值很少，但某个状态可能占九成行；`tenant_id` 取值很多，但单个租户只占很小一部分。优化器根据统计信息估算成本，设计者则要判断估算是否接近真实分布。

MyBatis 的动态 SQL 会让同一条语句生成不同形状。`<if test="status != null">` 可能让实际 SQL 跳过联合索引的前导列；`${}` 拼接还会带来注入风险，并让 SQL 难以稳定复用。先看最终执行的 SQL，而不是只读 Mapper XML。

```sql
-- 点查：测评结果详情
SELECT id, user_id, score, summary, created_at
FROM assessment_result
WHERE id = ?;

-- 列表：某租户下已支付订单，按时间倒序
SELECT id, status, created_at, amount
FROM orders
WHERE tenant_id = ?
  AND status = 'PAID'
ORDER BY created_at DESC
LIMIT 20;

-- 后台统计：时间窗口内按状态聚合
SELECT status, COUNT(*)
FROM orders
WHERE tenant_id = ?
  AND created_at >= ?
GROUP BY status;
```

## 选择性只是第一层

过滤后剩余行数越少，索引通常越有价值。可以用 `COUNT(DISTINCT column) / COUNT(*)` 估算可选择率，但不要把它当成唯一标准。一个取值很多的字段，如果查询总是带范围条件，单列索引仍然可能低效；一个取值很少的字段，如果和租户、时间组合后能稳定缩小范围，反而值得进入联合索引。

`SHOW INDEX FROM orders;` 里的 `Cardinality` 是优化器采样后的估算值，不是精确统计。数据倾斜、批量导入或长期未更新统计信息时，它可能偏离真实分布。MySQL 8 可以用 `ANALYZE TABLE` 更新统计信息，也可以对关键列建立直方图；但这些操作本身有成本，应该在维护窗口执行，并把执行前后的执行计划一起记录。

InnoDB 的主键选择会放大到所有二级索引。二级索引的叶子节点保存索引列和主键值，主键越长，每个索引页能容纳的条目越少，缓存命中率越差。自增主键顺序写入，页分裂较少；随机 UUID 会把插入分散到整棵树，写放大更明显。如果业务需要外部标识，可以把 UUID 作为唯一键，内部仍使用紧凑、稳定、单调的主键。

## 联合索引的顺序来自查询形状

联合索引遵循最左前缀原则。对于 `(tenant_id, status, created_at)`，从 `tenant_id` 开始的连续等值条件可以有效定位；跳过第一列直接查 `status`，通常无法按预期缩小范围。SQL 里条件的书写顺序不影响匹配，但索引列的顺序必须先满足最左前缀。

```sql
CREATE INDEX idx_orders_tenant_status_time
    ON orders (tenant_id, status, created_at);
```

常见策略是等值条件在前，范围或排序字段在后。上面的查询里，`tenant_id` 和 `status` 是等值条件，`created_at` 同时承担范围与排序，因此顺序合理。若把 `created_at` 放在第二位，`status` 就可能无法继续用于精确定位。

范围条件之后的列通常难以继续用于定位。`(a, b, c)` 上的 `a = ? AND b > ? AND c = ?`，`c` 仍可通过索引下推在索引层过滤，但不能再缩小 `b` 的范围。执行计划里的 `Using index condition` 说明发生了索引下推，它减少回表，但不等于把范围变成了等值。

排序方向也要与索引一致。MySQL 8 支持降序索引，可以让 `ORDER BY created_at DESC, id DESC` 与索引方向匹配；早期版本对混合方向的处理更受限。排序字段不唯一时，追加主键作为次级排序条件，既能让分页稳定，也能减少翻页时重复或遗漏。是否真的消除了 `filesort`，仍要以执行计划为准。

有据的 `Post` 模型提供了一个很直观的例子：跨帖对比表要按“帖子主数字”排序，而数字原本放在 JSON 字段里。JSON 路径排序既吃不到索引，也比较慢，所以项目把 `metricValue` 抽成独立列，并建立 `@@index([genre, status, deletedAt, metricValue])`；推荐流则用 `@@index([hotScore, status, deletedAt])` 取热度前 N 条。索引列不是猜出来的，而是从真实排序和过滤条件反推出来的。

MindType 的 `test_record` 初始迁移只有 `idx_test_record_user(user_id)`。草稿续测查询是 `user_id + status + test_type`，再按 `updated_at` 倒序取第一条；单列索引能先缩到某个用户，但同一用户有多条记录时仍要回表过滤和排序。评审时可以测试 `(user_id, status, test_type, updated_at)` 是否能减少扫描，但在没有代表性数据和执行计划之前，不要直接下结论。

> 联合索引不是把三个单列索引装进一个名字，而是按照列的顺序建立一套新的排列方式。

## 覆盖索引是一次成本交换

当查询所需字段都包含在索引中时，存储引擎可以直接从索引得到结果，这就是覆盖索引。`EXPLAIN` 的 `Extra` 出现 `Using index`，通常说明不需要回表。它能减少随机 I/O，但不意味着应把所有列都塞进索引。更宽的索引会占用更多页，降低缓存效率，也增加每次写入的维护成本。

`SELECT *` 会掩盖真实字段需求，也让覆盖优化变得脆弱。明确返回列既有助于评估索引，也降低表结构变化对查询的影响。对于列表页，先问清楚卡片真正展示哪些字段；如果只需要标题、状态和时间，就不必把正文和扩展属性一起带出来。

```sql
-- 宽索引：覆盖列表所需字段，但页面占用更大
CREATE INDEX idx_orders_list_cover
    ON orders (tenant_id, status, created_at, amount);

-- 查询只取列表需要的列，才有机会走覆盖索引
SELECT id, status, created_at, amount
FROM orders
WHERE tenant_id = ?
  AND status = 'PAID'
ORDER BY created_at DESC
LIMIT 20;
```

覆盖索引仍然要读索引页，不是零成本。它适合高频、字段稳定的列表查询；如果返回列经常变化，维护一个不断加宽的索引，通常不如接受回表。把回表次数、索引页大小和缓存命中率放在一起看，才能判断这笔交换是否划算。

`EXPLAIN` 反映的是优化器基于当前统计信息做出的选择，不是永久承诺。重点看访问类型、实际使用的索引、估算扫描行数、过滤比例和额外信息，而不是只盯某一个字段。MySQL 8.0.18 之后可以用 `EXPLAIN ANALYZE` 查看实际执行时间和循环次数；估算行数与实际行数差距很大时，先检查统计信息和参数分布，再决定是否调整索引。

## 写入成本与索引债

每次插入、更新和删除都可能维护多个索引。高频写入表上的重复或低价值索引，会转化为持续的存储与 I/O 成本。更新索引列尤其需要谨慎，因为它可能同时引起记录移动和索引维护。

可以用 `sys.schema_unused_indexes` 和 `sys.schema_redundant_indexes` 找候选，但它们只说明“可能没用”，不说明“可以删除”。低频的月度任务、灾备查询和导出 SQL 可能长期不出现，却在关键时刻依赖某个索引。删除前要覆盖完整业务周期，并在预发布环境回放代表性查询。

新增索引也要考虑发布方式。在线 DDL 并不总是无锁，`ALGORITHM=INPLACE, LOCK=NONE` 能否成功取决于版本、列类型和操作类型。先在影子表或预发布环境验证，再安排低峰执行；同时准备回滚语句，避免上线后发现写入延迟上升却无法快速撤销。

## 一份可执行的检查顺序

1. 收集查询：按形状分组，记录参数分布、频率和返回列。
2. 检查写法：函数包列、隐式类型转换、前导通配符、跨列 `OR`、深分页都会让索引失效或低效。
3. 看计划：用 `EXPLAIN` 判断访问路径，用 `EXPLAIN ANALYZE` 校准估算；保存优化前后的基线与耗时。
4. 评估写入：新增索引会不会拖慢核心写入？是否与现有索引重复？是否有更窄的替代？
5. 小步上线：一次只改一个变量，观察慢查询、锁等待和写入延迟，保留可回滚的 DDL。
6. 定期复查：数据增长、统计信息变化和业务查询演进都会让旧索引失效。

几个高频失效场景值得单独记住：`WHERE DATE(created_at) = ?` 会让列上的索引难以使用，改写成时间范围；字符串列与数字比较可能触发隐式转换；`LIKE '%keyword%'` 无法利用普通 B+ 树前缀，应该考虑全文索引或独立的检索系统；`OR` 连接不同列时，优化器未必能合并索引，必要时拆成 `UNION ALL` 或调整联合索引。

深分页也是索引设计的一部分。`LIMIT 100000, 20` 需要先跳过大量记录，即使用到索引，代价仍然随偏移增长。列表接口更适合游标分页：把上一页最后一条的排序键传给下一页，让查询从确定位置继续。接口层的写法在[另一篇笔记](/posts/spring-boot-api-design/)里展开，这里只需记住：索引顺序、排序稳定性和分页方式必须一起设计。

像 MindType 的测评结果表、有据的帖子列表，字段并不多，但查询形状差异很大。结果详情是点查，信息流是“状态 + 时间 + 热度”的组合过滤，后台汇总又是范围聚合。先承认它们不是同一条查询，再决定索引，通常比追求一个“万能索引”更可靠。

好的索引设计是一轮轮测量后的取舍：目标不是索引数量最多，而是用尽可能小的维护成本，让重要查询获得稳定、可解释的执行路径。
